# コードの構成

## 構成
- `scripts/osu/` … パーサ、スライダー軌道、osz 読み込み、星評価の推定(難易度の基準用)
- `scripts/mods.gd` … MOD の定義と効果の合成
- `scripts/game/` … 弾幕生成(`pattern_gen.gd`)、進行(`game_sim.gd`)、弾(`bullet_field.gd`)、効果音(`sfx.gd`。ファイルの読み込みは `scripts/sfx_bank.gd`)、画面
- `scripts/ui/` … UI の触り心地: 効果音(`ui_sfx.gd`)、全ボタンへの自動の弾み(`juice.gd`)、粒と輪(`ui_fx.gd`)、画面切り替えの幕(`screen_wipe.gd`)。タイトル画面(`title_screen.gd`)、遊び方パネル(`howto_panel.gd`)、選曲画面(`menu_screen.gd`)、設定パネル(`options_panel.gd`。トグルのカードは `toggle_card.gd`)、MOD パネル(`mod_panel.gd`)、リザルト(`result_screen.gd`、ランクのメーター `rank_meter.gd`、体力のグラフ `hp_graph.gd`)、共通スタイル(`ui_style.gd`)
- `scripts/ui/lazer/` … lazer 風の UI(スタイル `lazer_style.gd`、枠 `lazer_chrome.gd`・`lazer_frame.gd`、斜めのボタン `lazer_button.gd`、アイコン `lazer_icons.gd`、ロゴ `lazer_logo.gd`、画面: `lazer_title.gd` / `lazer_menu.gd` / `lazer_game.gd` / `lazer_result.gd` / `lazer_multi.gd`、設定 `lazer_options.gd`、遊び方 `lazer_howto.gd`、MOD `lazer_mods.gd`、確認 `lazer_dialog.gd` / `lazer_quit.gd`、プレイヤー `lazer_player.gd`・`now_playing.gd`、プレイリスト `lazer_playlist.gd`(データは `scripts/playlist.gd`)、プロフィール `lazer_profile.gd`・`lazer_profile_chip.gd`(データは `scripts/profile.gd`)、更新 `lazer_update.gd`、ボスのゲージ `lazer_boss_gauge.gd`)
- `scripts/chart_cache.gd` … **譜面の読み込み結果の保存**(曲を選んだときの待ちを短くし、全曲の難易度をあらかじめ用意する)。曲を選ぶと、全難易度の .osu の解析(スライダーの曲線まで)と弾幕の生成をしていた(1 曲 140〜540 ms)。同じ曲なら毎回同じ結果なので、`user://chart_cache/` に、大きさの違う 2 つに分けて保存する: **統計(.dcs)**= 曲ごと・弾幕の作り方(v1 / v2)ごと。全難易度の譜面の情報(`Beatmap.to_meta`。ノーツは含めない)と、弾幕の統計(Lv・★・弾速・弾の大きさ・弾数など。発射の一覧は含めない。`ChartCache.stub_of`)で、1 曲 1〜11 KB。難易度の表示・難易度順・長さ順には、これだけで足りる。**発射の一覧(.dce)**= 譜面ごと。プレイに使う弾幕の全部(1 譜面 20〜130 KB)で、**選んだ(遊ぶ)譜面の分だけ**、あとから作って残す(合計 96 MB を超えたら、古いものから捨てる)。統計から開いた曲の弾幕は、統計だけの「stub」で、選んだ譜面の発射の一覧は、裏で用意する(`SongBrowser.ensure_full`。保存してあれば 10 ms、なければ作って 60〜230 ms。それまで「プレイ」は押せない)。統計から開く読み込みは 35〜45 ms(保存なしは 220〜550 ms)。保存した譜面は「軽い版」(`Beatmap.from_meta`)で、ノーツ(`hit_objects`)は使うときに、その譜面のファイルだけを開き直して読む。**弾幕を変える MOD(加速・弾数・弾速・弾の大きさ・自機の大きさ。`Mods.pattern_neutral`)を付けたとき**は、Lv を測り直すのに全譜面の発射の一覧が要るので、全譜面ぶんを用意し直す(`needs_style_reload`)。**全曲の難易度の準備**: 保存の統計がない曲を、起動したあと裏の 1 スレッドで 1 曲ずつ処理して統計を保存し(`SongBrowser.start_prep`。1 曲 0.5 秒前後。曲の読み込み中・プレイ中は待つ。左の「難易度を準備しています… n / m」に進み具合)、全曲の MOD なしの Lv を `song_art.json` の `levels` に残す(難易度順・難易度の表示に使う。測ったときの弾幕の作り方の版 `ChartCache.stamp_tag` つき)。曲のファイルの大きさ・更新時刻が変わる / 弾幕の作り方(アプリの版 + ソースから動かしているときは生成に関わるスクリプトの更新時刻)が変わると、別のファイル名になって、古い保存は読まない。壊れた保存は捨てて作り直す。前の形式(.dcc)と古い一時ファイルは、起動のあと 1 回、整理で捨てる。**前の曲の弾幕は別スレッドで手放す**(保存から読んだ弾幕はキャッシュと共有しないので、主スレッドで解放すると 20〜30 ms 止まって、一覧の動きが跳ぶ)。**プレイ中は、選曲の一覧の画像・難易度の取得(`SongArt`)も止める**(`SongArt.paused`。`Main._swap_now` が、画面がプレイのときだけ true にする。初めて選んだ曲では、一覧の作業が溜まったまま、プレイ中に別スレッドの解析や画像の変換・保存が走り、25〜30 ms の長いフレームが数回出ていた。`--prof-play <曲名> secs=25` で、プレイ中の 22 ms を超えたフレームを測れる)。
- `scripts/song_library.gd` … 曲(.osz)の探索(タイトルと選曲が共通で使う)と、譜面の MD5 から曲を探す(マルチプレイ)
- `scripts/net/` … マルチプレイ: 通信層(`net.gd`)、招待コード(`invite_code.gd`)、プレイ中の同期(`mp_game.gd`)。画面は `scripts/ui/multi_screen.gd`

## 処理と描画の分離(判定は 1000 Hz)
- ゲームの進行・当たり判定・スコア(`game_sim.gd` / `bullet_field.gd`)は、描画・音声・ノードに依存しない純粋なロジックです(ヘッドレスのテストがそのまま回せます)。描画は `arena_view.gd` / `game_screen.gd` が sim の状態を読むだけです。
- 判定は描画のフレームレートに縛られません。`game_screen.gd` は 1 フレームごとに、曲クロックに追いつくまで sim を **`SIM_STEP` = 1 ms 刻み**で進めます(60 fps なら 1 フレームに約 17 回、144 fps なら約 7 回)。当たり判定・被弾時間・ゲージ・グレイズは ms 単位で計算され、発射時刻の誤差も 1 ms 以内です。入力は、キーボードなら各ステップで押している方向を、マウスならそのフレームの移動量を各ステップに等分して渡します。
- **曲クロックの滑らかさ**: 音声クロックはミキサーのかたまり単位でしか更新されないため、そのまま使うとフレームごとの増分がばらつき(止まって次に跳ぶ)、弾の移動距離がフレームごとに違ってカクついて見えます。そこで曲クロックは描画のフレーム時間で滑らかに進め、音声とのずれだけを `CLOCK_PULL` = 4/秒の割合でゆっくり寄せます(0.1 秒以上ずれたら直接合わせます)。実測(約 320 fps): 増分のばらつきは標準偏差 1.22 ms → 0.08 ms、最大 5 ms → 0.34 ms、停止フレームは 6% → 0。音声とのずれは平均 0 ms・最大 9 ms 程度(`--smoke-clock`)。
- 処理が重く 1 フレームに `SIM_MAX_STEPS`(100)回では追いつかない場合だけ、刻みを粗くして時刻を合わせます(通常は起きません)。
- 費用の実測(`tests/test_sim.gd ... 1khz`): 1 ステップ約 0.02〜0.04 ms(弾 100〜200 発)で、1000 Hz 進めても実時間の 2〜4% 程度です。
